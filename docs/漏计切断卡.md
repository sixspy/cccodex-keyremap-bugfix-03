# 冲突漏计切断卡

- 卡号：漏计切断-2026-11-20
- 择定日期：2026-11-20（当日锁定，禁止改口）
- 适用链路：批重映（`POST /api/batch-remap`）与冲突查询（`GET /api/conflicts`）
- 库：本题目录 SQLite（`data/app.db`，测试用同目录语义的临时库）

## 一、症候

批重映结束旗为绿、批回执冲突计数为零，但批内含无映射旧键；该旧键被降级成“以旧键当新键”写入正式区，形成脏新键。对账按“冲突应收”口径失败，冲突列表查不到该批的无映射键，入站残留与正式区不同态。

## 二、择定口径（二选一，甲乙互斥，不得混用）

**择定：甲路径。**

> 无映射键必须先插入冲突行，再允许批继续；否则整笔回滚，正式零增。

具体约束：

1. 扫描到无映射键时，先在**本批事务内**写入 `conflicts` 行（带 `batch_no`），成功后方可继续扫描后续键。
2. 冲突行写入失败，或事务内任一写入失败，整笔回滚：正式区本批零增、冲突区本批零增、入站残留不落。
3. 无映射键**永不**写 `formal_entities`。正式实体键只允许是当前生效映射版本的 `mappings.new_key`。
4. 有映射键照常写正式区，与冲突行同一事务提交，不得分事务提交、不得先写正式再补冲突。
5. 甲路径与乙路径（分轨同事务）互斥；本卡生效期间一律按甲路径实现，不得局部改用乙路径。

## 三、批锁约定

- 两批同时扫同一 `batch_no` 时，先到者持有批锁（`batch_locks.batch_no` 主键互斥），后到者**不得**进入扫描窗口。
- 后到者记一条 `batch_contention`（`batch_no`、`owner`=后到扫描号、`holder`=持锁扫描号），返回 423。
- 后到者不产生正式行、冲突行、批回执。

## 四、五处同态（缺一判失败）

同一批号的以下五处必须与批回执计数一致、互不矛盾：

| # | 面 | 数据源 |
|---|----|--------|
| 1 | 冲突列表 | `conflicts.batch_no` |
| 2 | 正式实体 | `formal_entities.batch_no` |
| 3 | 批回执 | `batch_receipts`（conflict_count/formal_count/inbound_count） |
| 4 | 互证页 | `GET /api/attestation?batch_no=` |
| 5 | 入站残留 | `inbound_rows`（disposition 与两侧一致） |

## 五、拒写与记账

- 任何写入偏离本卡（尤其“无映射键写正式区”“批继续但冲突行缺失”）一律拒写，并在 `cut_deviations` 记 `漏计偏了：<细节>`。
- 禁止只改冲突数字样式（前端计数、回执字段改名、把冲突数硬编码为零/应收账款）。此类改动直接判失败。

## 六、测试闸门

1. 先造夹具：无映射键混批、冲突为零、脏新键入正式 → `fixtures/batch_unmapped_mixed.json`，落 `tests/test_conflict_leak.py` 见红。
2. 再造抢批夹具：同批号两写 → `fixtures/batch_contention.json`，落 `tests/test_batch_contention.py` 见红。
3. 两条红测齐备后，才允许改冲突写入路径。
4. 禁止跳过失败测、禁止无测直接改数字。
5. 全绿判据：冲突可查，且脏键不在正式区。

## 七、验收

- `pytest` 全绿。
- `GET /api/conflicts?batch_no=` 可查到无映射键。
- `GET /api/formal?batch_no=` 无脏新键。
- `GET /api/attestation?batch_no=` 返回 `ok=true`，五处计数同态。
